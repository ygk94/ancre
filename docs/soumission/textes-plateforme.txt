BIO / ONE-LINER

Sybil-resistant ERC-8004 reputation a contract can check before paying.

(Alternative, si la limite le permet : "Reader-anchored ERC-8004 reputation that travels beyond one hop, checked by the contract that pays.")


DESCRIPTION

ANCRE is a reputation layer for AI agents that a smart contract can read before it pays. It is built on ERC-8004, the standard that gives agents an on-chain identity and lets anyone leave feedback about them. ERC-8004 deliberately leaves one problem open. Anyone can rate any agent, for free, and the standard says in its own text that Sybil attacks are possible. Filtering is left to the reader: calling getSummary without a list of trusted raters simply reverts. The reader is expected to know whom to trust, but is given no tool to work it out. ANCRE is that tool. We do not build another registry or another agent passport. We build the layer the standard hands to the reader.

The problem is not theoretical. We re-read the canonical ERC-8004 registries on Monad mainnet directly on-chain. On 28 September 2026 they held 10,262 agents and 9,283 feedback entries. 83% of all that feedback points to a single agent, Eve-8004, and comes from 7,665 agents created in about 48 hours. Because 117 of those ratings are set to 1e38, Eve's naive average is 1.53 × 10^36. Any application that ranks agents by their average rating puts that agent first. Requiring proof of payment does not help: the farm paid, and the raters were funded by the same owner. In a random sample of 150 of Eve's raters, every single one received its first MON from Eve's owner, 11.0 MON each. A receipt can be true and still come from a farm. We ran the same edge rules over seven chains with Envio HyperSync: under our reference schema, less than 5% of ERC-8004 feedback survives as a usable trust edge on any of them, and on Monad only 0.12% does. Since that schema was built from Monad's tags, the figures for other chains are a lower bound, not a verdict.

ANCRE starts from one idea: trust does not exist in the absolute, it exists from someone's point of view. There is no global score. The ERC-8004 authors themselves consider a single global score dangerous, and a post in the standard's discussion thread (ethereum-magicians #309) asked for exactly this approach, without an answer so far. Each reader, whether a company, a DAO or a buyer agent, chooses a small set of anchors it already trusts. ANCRE then computes Personalized PageRank, from the EigenTrust family, starting from those anchors and following the graph of ratings between agents. Trust only flows along ratings given by agents the anchors can reach. A farm of thousands of accounts rating each other therefore receives nothing, unless one of the reader's anchors vouches for it. What sets ANCRE apart from a list of trusted raters is that trust travels beyond one hop, with a formal bound. An agent that none of your anchors rated can still be trusted, because an agent they rated vouches for it, and the trust that can leak into a Sybil group is capped by a known formula. A trusted list tells you whose ratings count. ANCRE tells you whose ratings count because someone you trust vouched for them, and proves it to your contract. Two readers can look at the same registry and see two different rankings, and that is intended.

The computation happens off-chain, but the result is certified on-chain. A solver submits a certificate: the graph in calldata and, for each anchor, a trust vector. The AnchoredReputation contract recomputes one PageRank step and accepts the vector only if no value exceeds its recomputed one. Because the PageRank map is monotone, such a vector is an exact lower bound on every agent's true trust. That property is classical; what is new is enforcing it inside the contract that pays. At the strongest level, which we call Registry-verified, the contract also re-reads every edge from the live ERC-8004 registry, so a fabricated or inflated rating is rejected at submission. Omitting or diluting edges is still possible, and anyone can prove it on-chain afterwards, which widens the certificate's bounds. We present the guarantee with its level and its limits.

The certified score is then used where it matters: at payment time. TrustGatedPayer is a smart account (ERC-1271) that holds the USDC used to pay other agents over x402. Its signature check calls passesAnchorPolicy on the ANCRE contract, which applies the policy committed in the reader's anchor set. Trust is computed leaving out the largest single anchor, so one stolen anchor key is never enough to make the payer pay. If the provider is below the reader's threshold, or if one of the anchors has vetoed it, the payment cannot settle. The refusal comes from the contract, not from an interface that could be bypassed. A veto is read live from the registry: when an anchor flags a provider that went bad, every payer relying on that anchor refuses the very next payment, one block later, without waiting for a new certificate. We also wrote a plugin for the MetaMask Agent Wallet, mm ancre, which checks trust before the agent signs anything. If ANCRE refuses, only a human can force the payment, from their own wallet, and the agent has no path to do it alone.

On the real Monad registry, with two anchors, Eve-8004 ends up with a trust mass of exactly 0, compared with its naive average of 1.53e36. The few honest ratings that remain form a short chain: both anchors rate agent #18, and #18's wallet rates agents #2 and #3, which receive a positive, certified score at the second hop, although no anchor ever rated them. That honest graph is very small today, so ANCRE answers "unknown" for most agents. This is the correct answer, and the positive side of our demo relies on our own agent traffic.

Monad is what makes this practical. Blocks come every 0.3 seconds (we measured 0.302 s over 1,000 blocks), so a veto stops payments one block after it is posted. We recertify on every change of the graph rather than on every block. In our fork tests, it took 390 ms from a graph change to the on-chain receipt. The Registry-verified certificate for a 300-edge demo graph costs 15.0 million gas and fits in a single transaction; for the real mainnet graph it costs about one million gas. The trust check adds about 183,000 gas per payment, and refusing an unknown agent costs 29,000 gas. The canonical ERC-8004 registries are deployed on both Monad mainnet and testnet, so we work against the real ones. The standard we propose stays chain-agnostic, since ERC-8004 is deployed on many chains (we scanned seven of them with Envio HyperSync), but Monad is where its strongest verification level becomes routine.

The project includes the verifier and payer contracts in Solidity, tested with Foundry against forks of Monad mainnet and testnet. It also includes the PageRank solver and certification service in Python, an Envio HyperIndex indexer running on Envio Cloud for Monad mainnet, Monad testnet and Optimism, and the MetaMask Agent Wallet plugin. Alchemy webhooks trigger recertification when the graph changes, and Alchemy's Transfers API explains a score by showing where a rater's funds came from. Alongside the code, we wrote a draft ERC, "Anchored Reputation for Trustless Agents", with test vectors and an independent verifier. ANCRE is meant to be its reference implementation.

We credit the prior work we build on. OpenRank (Karma3) already prototyped verifying a PageRank fixed point on-chain. trustgraphs computes anchored PageRank with zero-knowledge proofs, on EAS rather than ERC-8004. monad-agent-trust studies payment provenance on the same Monad data; that work is complementary, and in our standard it can be plugged in as an additional filter on edges. What ANCRE brings is the combination: anchors chosen by the reader, trust that propagates beyond one hop with a Sybil bound, unmodified ERC-8004 as the data source, certification at the speed of the chain, and a score read by the paying contract itself.

The project was built with heavy use of an AI coding agent (Claude Code), as disclosed in the README. Every number in this description comes from a script in the repository and can be re-run.


GO-TO-MARKET AND USER ACQUISITION

Our first users are the people who lose money when an agent's reputation lies: anyone who pays AI agents automatically. Today that means buyer agents and applications paying for tool calls over x402, agent marketplaces that rank providers, and companies starting to let their own agents spend a budget. They all face the same choice ERC-8004 leaves open: which raters to trust. On Monad mainnet, 83% of the feedback comes from one farm, so the naive answer is already wrong. We do not need to convince these users that the problem exists. We can show it to them on their own chain, and show the payment that ANCRE refuses.

Adoption starts with the standard, not with a sales pitch. ANCRE is the reference implementation of a draft ERC, "Anchored Reputation for Trustless Agents". After the hackathon we will open the pull request on ethereum/ERCs and answer the post in the ERC-8004 discussion thread that asked for reputation relative to reader-chosen anchors. That thread is where the builders of agent infrastructure already gather, so the standard brings us our first integrators. Because the interface is chain-agnostic and ERC-8004 is deployed on more than 40 chains, every integration we win on Monad can be reused elsewhere, while Monad remains the chain where certification is fast and cheap enough to run on every graph change.

We then go where payments are decided. The trust check is one call, passesAnchorPolicy, and our payer contract wraps it around an x402 payment, so an agent can adopt ANCRE without changing how it pays. We will publish the payer as a drop-in contract, keep the Envio indexer open source, and offer a read API that returns every score together with its certificate, so that nobody has to trust us to use it. Our first target partners are the teams already working on the same data: the Monad x402 facilitator, ERC-8004 explorers such as 8004scan, and the projects that check payment receipts or payment provenance. In our standard, their signals plug in as edge filters, so they gain from ANCRE instead of competing with it.

Cold start is the real challenge, and we plan for it. A trust graph is only useful once honest agents rate each other, and the honest graph on Monad is tiny today. We will seed it with a few public anchor sets whose members and rules are published, and with design partners: teams that run several agents and are willing to rate the providers they actually pay. Every certified payment they make adds an honest edge, so each new partner makes the graph more useful for the next one. Companies get the same product for their own perimeter: a private anchor set turns any public registry into their own trust domain, with no private infrastructure to run.

The business model follows the cost. Reading a score is free for everyone. The owner of an anchor set pays for its certification, which on Monad costs little enough to repeat on every change of the graph, and we will charge a fee for operating that service, acting as a reputation oracle whose every answer can be verified on-chain. We will measure success by the number of anchor sets certified, the number of payments that go through a trust check, and the number of honest edges in the graph, rather than by the number of agents registered.

BOUNTY ENVIO — Best Use of Envio
------------------------------------------------------------------------------
(Critères de la fiche, 27/09 : profondeur d'usage — multichain, schéma non trivial, entités dérivées, HyperSync pour l'analytique ; produit qui marche ; originalité ; qualité. Livrables : dépôt public avec config.yaml, schema.graphql, handlers ; un consommateur ; une démo courte.)

Envio is ANCRE's data layer, not an add-on.

1. One HyperIndex indexer, three chains. It runs on Envio Cloud and follows the ERC-8004 registries on Monad mainnet, Monad testnet and Optimism. Agent ids are only unique per chain, so each chain is indexed separately and the cross-chain view is built at query time. Identity (owners, agent wallets, operators) is rebuilt from events alone, never from historical eth_calls, and a consistency script checks it against the chain head.

2. Derived entities that carry ANCRE's rules. The schema keeps an append-only history, a current state rebuilt from events, and a layer of normative trust edges (RefEdge): the latest non-revoked rating per rater, agent and tag, with every rejection typed (measurement tag, out of bounds, controller of the target…). These are exactly the rules of our Python solver. A parity test compares the two on the real history of all three chains: zero differences (5 Oct 2026). The solver builds its graph straight from the indexer's GraphQL.

3. Auditing every certificate. A handler decodes each ANCRE certificate from the transaction calldata and compares it with the registry state the indexer holds. A fabricated, inflated, diluted or omitted edge becomes a Discrepancy entity with the proof ready to submit on-chain; a per-set health entity feeds the demo screen. On 11 October the official anchor set showed 10 certificates, all audited, status CLEAN, zero open discrepancies; the indexer also picked up and audited a second set (the Mera set) on its own.

4. HyperSync analytics across seven chains. A survival scan replays the same edge rules over the ERC-8004 deployments on Monad, Monad testnet, Ethereum, Base, Arbitrum, Optimism and Polygon: under our reference schema, less than 5% of feedback ever becomes a trust edge, 0.12% on Monad. HyperSync reads Monad's full history in about 17 seconds.

Links: indexer repository https://github.com/ygk94/ancre-indexerv2 · GraphQL endpoint https://indexer.dev.hyperindex.xyz/38cf597/v1/graphql · Envio video https://youtu.be/hErys6rsqvo · main demo https://youtu.be/YcCupzYoTDo.

BOUNTY MERA — One Passkey, Many Keys (Monad Foundation)
------------------------------------------------------------------------------
(Critères de la fiche, 27/09 : nouveauté, loin du « passkey wallet » ; usage correct des primitives, sels cloisonnés, rien de sensible persisté ; test multi-appareils EN LIVE. Exclu : signer des transactions depuis un compte wallet.)
(12/10 : porte P4 passée — même passkey iCloud, mêmes clés d'époque 0 et 1 sur Mac Safari et iPhone. La pré-rotation on-chain N'EST PAS implémentée : ne pas la promettre. Texte réel ci-dessous.)

In ANCRE, an anchor is a rater that a reader trusts to start with, and one anchor's veto stops every payer that relies on it. That makes an anchor's key the most sensitive key in the system. We derive anchor keys from a passkey with Mera: one PRF salt per epoch gives one independent secp256k1 key per epoch, so one passkey yields many anchor keys and nothing is ever stored. The keys are rebuilt on demand from the passkey alone.

What runs today, on Monad testnet (12 October). On rpId ancre-xyz.netlify.app, the same passkey, synced through iCloud Keychain, re-derives exactly the same epoch-0 and epoch-1 keys on a Mac (Safari) and on an iPhone (Safari); the page checks it address by address and fingerprint by fingerprint. Epoch key 0 (0xe3c8…309b) is a real anchor of an ANCRE anchor set registered on our verifier contract, next to two other anchors, with its own trust-gated payer. From the page, one Touch ID opens a Mera signing session on that key, which signs an ERC-8004 rating with tag "slash" against a provider; the browser broadcasts it (tx 0x7884e13e…0dcfed, block 70,462,375). The payer reads that veto live and refuses the next payment to that provider (reason ANCRE_STATUS, status VETOED). Each epoch key is an anchor's role identity: it holds only gas for its ratings, never the funds being paid.

Next: commit the digest of the next epoch key on-chain, so that a compromised anchor can rotate to its next key with one signature, without changing the reader's anchor set (designed in the draft ERC, not implemented yet).

Links: try it https://ancre-xyz.netlify.app/mera/ · code app/src/mera/ and demo/mera.ts in https://github.com/ygk94/ancre · Mera video https://youtu.be/kZRyA5Alos8.

BOUNTY ALCHEMY — Best Projects using Alchemy
------------------------------------------------------------------------------
(Fiche officielle copiée par Hugo le 06/10 : projet fonctionnel déployé sur Monad, intégration SIGNIFICATIVE d'au moins un service Alchemy. Critères : qualité de l'intégration, exécution technique, utilité et innovation. Demandé : une description de l'intégration ; vidéo OPTIONNELLE de 2 minutes au plus. Mise à jour du 10/10 (chantier alchemy-live, rapport docs/chantiers/rapports/alchemy-live.md, doc jury docs/ressources/alchemy-integration.md) : l'intégration est codée et testée ; il reste à remplir les ⟦CHECK⟧ avec la ligne TIMELINE du premier vrai webhook.)

ANCRE uses Alchemy at the two moments where the product needs the chain to speak first.

1. An Alchemy Custom Webhook triggers recertification. A certificate must change when the trust graph changes, and only then: not on a timer, not on every block. One webhook on Monad testnet watches the ERC-8004 Reputation and Identity registries (ratings, revocations, transfers, wallet changes, upgrades) and our AnchoredReputation contract (certificates, proofs). Our receiver checks the HMAC signature, keeps only the events that can change the certificate (a rating whose author carries trust, a change to an agent in the graph), pulls the registry state at that block from our Envio indexer, recomputes the certificate and submits it through the Alchemy Monad RPC, which carries every chain read and transaction of the certifier. The new certificate comes back through the same webhook and is audited. Measured on 10 October with signed payloads rebuilt from real testnet logs: 3.6 s from webhook reception to a certificate ready to send, identical to the one on chain. Measured live on 10 October over 14 real deliveries: a median of 1.3 s from the block's timestamp to webhook reception (0.7 to 2.1 s, timestamps at one-second resolution), with the block already Finalized at reception in 17 of 18 deliveries; a few later deliveries took 16-17 s, so a poller stays as a fallback. End to end, live on 10 October: an anchor's rating in block 69,834,805 reached our receiver 1.1 s later (block Finalized), Envio served the registry at that block within 57 ms, and the new certificate landed on chain in block 69,834,822: 17 blocks and 6.3 s after the webhook (tx 0x84785a94…8046). The receiver then audited its own certificate through the next webhook: no discrepancy.

2. Alchemy's Transfers API answers "why zero?". ANCRE gives Eve-8004, the most-rated agent of the Monad registry, a trust of zero from the reader's anchors alone. The agent page then shows a public fact from alchemy_getAssetTransfers: in a random sample of 150 of its 7,665 raters, every one received its first MON from the address that owns Eve-8004, exactly 11.0 MON each (measured 10 October; the script and its output are in the repository). The page re-checks a few raters live through a server function that holds our Alchemy key. ANCRE does not need this data to reach zero; it lets anyone see that the zero matches the chain.

Alchemy video: https://youtu.be/mhPeqNbootc · details: docs/ressources/alchemy-integration.md in https://github.com/ygk94/ancre

PROGRESS UPDATE — version du 12/10 (finale)
------------------------------------------------------------------------------

As of 12 October, ANCRE runs on Monad testnet and mainnet next to the canonical ERC-8004 registries. On mainnet, the verifier contract is deployed at 0x0Da1579233E7Cb07a174986D059D59B1F293b30E and the trust-gated payer at 0x52f361A14A49fAB267703203f833b997B9cF5Dc0 (testnet: 0x8bE6D3DD7F20b94cD9B1Ec51De199291B109da9B and 0xC9Db7a72960189e933a6B876A9359b5c605a5870). The demo runs a Sybil farm that really pays its target and gets zero trust, a stolen anchor key that cannot make the payer pay, an anchor veto that stops the next payment one block later, and an honest provider trusted at the second hop. The Envio indexer audits every certificate on Envio Cloud (10 certificates, all CLEAN, on 11 October), and an Alchemy webhook triggers a new certificate on each relevant rating (1.26 s from block to webhook and 6.4 s to the new certificate on chain, measured live on 11 October). An anchor whose keys come from a passkey through Mera posted a real veto from the browser on 12 October, and its payer refused the next payment. The draft ERC is ready for the ethereum/ERCs pull request after the hackathon. One limit we state openly: the honest graph on mainnet is still tiny, so the positive part of the demo uses our own agent traffic.

As of 5 October, the core of ANCRE is built and tested end to end on forks of Monad mainnet and testnet, against the real ERC-8004 registries. The verifier contract accepts certificates checked edge by edge against the registry, and the trust-gated payer refuses x402 payments to agents below threshold. The PageRank solver produces certificates that the contract accepts with identical results. The Envio indexer is live on Envio Cloud for Monad mainnet, Monad testnet and Optimism and matches the solver exactly. The MetaMask Agent Wallet plugin works in the real mm client, with an override that only a human can use. The draft ERC is written and passes the official linter.

Our measurements on mainnet confirm the problem we set out to solve: 83% of the feedback comes from a single farm whose target has a naive average of 1.53e36, and under ANCRE its trust is zero.

This week we deploy the contracts on Monad testnet, run a real payment through the x402 facilitator, then do a minimal run on mainnet. We are also building the live demo: a Sybil farm attacking a provider while ANCRE's score does not move, and a "circuit breaker" where one anchor's veto stops every payer at the next block. After that come the demo screen, the three-minute video and the public repository. One limit we will state openly: the honest graph on mainnet is still tiny, so the positive part of the demo uses our own agent traffic.
