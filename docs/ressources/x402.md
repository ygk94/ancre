## 0. Ce qu'il faut retenir (10 points)

1. **Le dépôt a déménagé.** La référence est `github.com/x402-foundation/x402`. `coinbase/x402` n'est plus qu'un fork de développement, dont le `main` est figé au 2026-04-21 (**DOC**, README de coinbase/x402). Specs lues au commit `02e80f3` du 2026-09-27.
2. **En-têtes v2** : `PAYMENT-REQUIRED` (serveur → client, 402), `PAYMENT-SIGNATURE` (client → serveur), `PAYMENT-RESPONSE` (serveur → client). Les trois portent du JSON encodé en base64. **`X-PAYMENT` est l'en-tête de la v1** (**DOC**).
3. **`exact` sur EVM** : EIP-3009 `transferWithAuthorization` par défaut. Permit2 et ERC-7710 sont des variantes. `validAfter` et `validBefore` sont des **secondes Unix** comparées à `block.timestamp` (**DOC** : spec et code Circle).
4. **`upto` sur EVM** : **Permit2 uniquement**, via `permitWitnessTransferFrom` et le proxy `x402UptoPermit2Proxy` (`0x4020A4f3…0002`). Le client signe un plafond, le serveur règle le montant réel (entre 0 et le plafond). Le témoin (*witness*) signé lie `to` **et l'adresse du facilitator** (**DOC**).
5. **Facilitator Monad (MESURÉ)** : v2, schémas `exact`, `upto` **et `batch-settlement`** (nouveau par rapport au 23/09), sur `eip155:143` et `eip155:10143`. Signataire `0x7f6a2850…Db86`. C'est un **fork Rust `x402-rs`** (`monad-developers/x402-rs`), pas le facilitator TypeScript de référence.
6. **USDC Monad mainnet `0x7547…b603`** : FiatToken **v2.2** derrière un proxy, `name`="USDC", `version`="2", 6 décimales. Il expose `transferWithAuthorization` et `receiveWithAuthorization` **en deux variantes** : `(v,r,s)` et `bytes signature` (**MESURÉ**). La variante `bytes` passe par `SignatureChecker`, donc par **ERC-1271 quand `from` est un contrat** (**DOC**, code Circle).
7. **Un contrat peut être payeur x402** : c'est **OUI** en `exact`/EIP-3009, via ERC-1271 (USDC v2.2 + facilitator Rust) et en `upto`/Permit2, où Permit2 appelle `isValidSignature` si `from` a du code (**DOC**, lecture de code, **non testé de bout en bout**). C'est la voie pour « un contrat refuse de payer » **sans modifier x402**.
8. **Piège EIP-7702** : le facilitator Rust classe une signature de 65 octets qui retrouve `from` par ecrecover comme une signature d'EOA. Il appelle alors la variante `(v,r,s)`, en ecrecover pur, **sans passer par `isValidSignature`**. Une garde logée dans un délégué 7702 est donc **contournable par le détenteur de la clé**. Pour une garde non contournable, il faut un **vrai compte-contrat, sans clé privée** (**DOC**, x402-rs).
9. **Aucune extension officielle ne touche la réputation ou ERC-8004.** Il existe 6 extensions de spec (bazaar, builder-code, auth-hints, offer-receipt, payment-identifier, sign-in-with-x) et 2 de sponsoring de gas. Le sujet est en revanche **très encombré côté propositions**, toutes ouvertes et non fusionnées : #931, #1024 (50 commentaires), #2803, #2300, #2641, #1395… (**DOC**, GitHub API). Presque toutes filtrent **le payeur, côté vendeur**. ANCRE filtre **le vendeur, côté payeur**, et le filtrage est certifié on-chain.
10. **SDK** : `@x402/*` **2.27.0** (publié le 2026-09-22), `x402` sur PyPI **2.24.0** (2026-09-22) (**MESURÉ**, registres npm et PyPI). Côté client, une garde ANCRE s'écrit en quelques lignes avec `x402Client.onBeforePaymentCreation(...)`, qui peut renvoyer `{abort:true}`, ou avec `registerPolicy(...)`.

## 1. Flux v2 (transport HTTP)

Sources : [x402-specification-v2.md](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md) · [transports-v2/http.md](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md) (**DOC**).

```
Client (agent)                 Serveur de ressource                 Facilitator                     Chaîne
    | GET /res                          |                                 |                             |
    |---------------------------------->|                                 |                             |
    | 402 + PAYMENT-REQUIRED: b64(PaymentRequired{accepts[...]})          |                             |
    |<----------------------------------|                                 |                             |
    | [choisit un accepts[i], SIGNE hors chaîne (EIP-712)]                |                             |
    | GET /res + PAYMENT-SIGNATURE: b64(PaymentPayload)                   |                             |
    |---------------------------------->| POST /verify {paymentPayload,   |                             |
    |                                   |   paymentRequirements}          |-- eth_call (simulation) --->|
    |                                   |<-- {isValid, invalidReason?, payer}                           |
    |                                   | [exécute le handler]            |                             |
    |                                   | POST /settle (même corps ;      |                             |
    |                                   |   en upto : amount = réel)      |-- tx transferWithAuth / --->|
    |                                   |<-- {success, transaction, network, payer, amount?}            |
    | 200 + PAYMENT-RESPONSE: b64(SettleResponse)                         |                             |
    |<----------------------------------|                                 |                             |
```

- **Flux par défaut `authorization`** : verify → ressource → settle → réponse. Les flux `upfront` (settle → ressource) et `escrow` (settle → ressource → settle) existent, et `extra.paymentFlow` est obligatoire quand le flux n'est pas `authorization`. Invariant de la spec : au moins un contrôle (verify ou settle) a lieu avant que la ressource ne s'exécute (§6.1).
- **`PaymentRequirements`** (`accepts[i]`) : `scheme`, `network` (CAIP-2), `amount` (unités atomiques, en chaîne de caractères), `asset`, `payTo`, `maxTimeoutSeconds`, `extra`. `extra.assetTransferMethod` et `extra.paymentFlow` sont des clés réservées. Le reste de `extra` dépend du schéma : pour EIP-3009, `name` et `version` du domaine EIP-712 (§5.1.2).
- **`PaymentPayload`** : `x402Version: 2`, `resource?`, `accepted` (copie de l'offre choisie), `payload` (propre au schéma), `extensions?` (§5.2).
- **`/verify`** est en **lecture seule** : il ne doit rien écrire on-chain (§7.1). Il répond `{isValid, invalidReason?, payer?, extensions?, extra?}`.
- **`/settle`** : même corps que `/verify`. Il répond `{success, errorReason?, payer?, transaction, network, amount?, extensions?}`. `settlement_pending` est un code **non terminal** : la tx a été diffusée mais sa confirmation est inconnue, et `transaction` contient alors le hash (§9).
- **`GET /supported`** : `{kinds:[{x402Version, scheme, network, extra?}], extensions:[], signers:{caip2: [addr]}}` (§7.3).
- **Codes HTTP** : 402 pour un paiement requis ou échoué, 400 pour un payload malformé, **412 `PERMIT2_ALLOWANCE_REQUIRED`** quand l'approbation Permit2 manque (schémas Permit2), 500 pour une erreur serveur.
- **Codes d'erreur standards** (§9) : `insufficient_funds`, `invalid_exact_evm_payload_authorization_valid_after|valid_before|value_mismatch|recipient_mismatch`, `invalid_exact_evm_payload_signature`, `invalid_network`, `invalid_payload`, `invalid_scheme`, `unsupported_scheme`, `invalid_transaction_state`, `unexpected_verify_error`, `unexpected_settle_error`, `settlement_pending`. Code propre à `upto` : `invalid_upto_evm_payload_settlement_exceeds_amount`.
- **Canal secondaire** : l'en-tête `EXTENSION-RESPONSES` circule entre facilitator et serveur et n'est **jamais** transmis à l'acheteur (§7.2.1).

## 2. Schéma `exact` (EVM)

Source : [schemes/exact/scheme_exact_evm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md) (**DOC**).

| `assetTransferMethod` | Mécanisme | Remarque |
|---|---|---|
| `eip3009` (par défaut) | `token.transferWithAuthorization(...)` appelé par le facilitator | USDC ; sans gas pour le client |
| `permit2` | `x402ExactPermit2Proxy` (`0x402085c248EeA27D92E8b30b2C58ed07f9E20001`) → `Permit2.permitWitnessTransferFrom` | le témoin `{to, validAfter}` lie le destinataire ; exige `approve(Permit2)` une fois |
| `erc7710` | `delegationManager.redeemDelegations(...)` (MetaMask Delegation Framework) | vérifié **uniquement par simulation** ; **non implémenté** par le facilitator Monad (aucun fichier 7710 dans x402-rs, **NON TROUVÉ**) |

**Payload EIP-3009** (champ `payload`) :
```json
{ "signature": "0x…(65 octets pour une EOA, arbitraire pour ERC-1271)",
  "authorization": { "from": "0x…", "to": "0x…(=payTo)", "value": "10000",
                     "validAfter": "0", "validBefore": "1740672154", "nonce": "0x…32 octets aléatoires" } }
```
Message signé (EIP-712, domaine `{name: extra.name, version: extra.version, chainId, verifyingContract: asset}`) :
`TransferWithAuthorization(address from,address to,uint256 value,uint256 validAfter,uint256 validBefore,bytes32 nonce)`. Typehash `0x7c7c6cdb…2267`, identique on-chain (**MESURÉ**).

**Vérification** : la signature doit retrouver `from`, le solde doit suffire, montant, fenêtre, token et réseau doivent correspondre, puis vient une simulation de `transferWithAuthorization`. **Règlement** : le facilitator appelle `transferWithAuthorization` et **paie le gas**. Il ne peut modifier ni le montant ni le destinataire.

**Temps** (**DOC**) :
- Le SDK client TS fixe `validAfter = "0"` et `validBefore = now + maxTimeoutSeconds` ([client/eip3009.ts](https://github.com/x402-foundation/x402/blob/main/typescript/packages/mechanisms/evm/src/exact/client/eip3009.ts)).
- Le facilitator TS refuse si `validBefore < now + 6 s` (marge de bloc) ou si `validAfter > now`.
- On-chain, chez Circle ([EIP3009.sol](https://github.com/circlefin/stablecoin-evm/blob/master/contracts/v2/EIP3009.sol)) : `require(now > validAfter)` (strict) et `require(now < validBefore)`, où `now` = `block.timestamp` en **secondes**. C'est la seule exception légitime à la règle « `block.number` pour les époques » (CLAUDE.md §7), et elle est imposée par le token, pas par nous.
- Anti-rejeu : `nonce` de 32 octets aléatoires, consommé par `authorizationState(authorizer, nonce)`. Il n'y a pas de nonce séquentiel, donc des autorisations parallèles sont possibles.

## 3. Schéma `upto` (EVM)

Sources : [scheme_upto.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/upto/scheme_upto.md) · [scheme_upto_evm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/upto/scheme_upto_evm.md) (**DOC**).

- **Permit2 uniquement.** La spec l'écrit explicitement : « EIP-3009 is not supported for upto because it requires exact amounts ».
- Le client signe `PermitWitnessTransferFrom`. `permitted.amount` est le **plafond**. Le témoin vaut `{to, facilitator, validAfter}` et `deadline` sert d'expiration (secondes). `spender` = `x402UptoPermit2Proxy` `0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002`.
- **L'adresse du facilitator est liée dans la signature.** Le client la lit dans `accepts[i].extra.facilitatorAddress`, que le serveur recopie depuis `/supported`. Chez Monad, elle vaut `0x7f6a2850669202519f0fe8aa912451238820db86` (**MESURÉ**).
- **`amount` change de sens selon la phase** : à `/verify` c'est le plafond (et il doit être **égal** à `permitted.amount`), à `/settle` c'est le montant réel, qui doit être ≤ plafond (0 est autorisé). À `/settle`, la signature se revérifie **sur le plafond**. Un règlement à 0 n'envoie aucune tx et l'autorisation expire.
- **Usage unique** : nonce Permit2. Pas de flux continu : c'est le rôle de `batch-settlement`.
- **Prérequis** : `USDC.approve(Permit2)` une fois. Sinon le facilitator répond **412**, ou passe par les extensions `erc20ApprovalGasSponsoring` / `eip2612GasSponsoring`.
- **Piège de version** (docs Monad, **DOC**) : `@x402/evm` **≥ 2.12.0**. Les versions 2.9.0 à 2.11.0 visent un ancien proxy `0x402039b3…0002`, absent de Monad (**MESURÉ** : code vide sur 143 et 10143).
- **Sécurité (spec)** : le client assume le risque jusqu'au plafond, puisque le serveur fixe le montant. Pour ANCRE, la piste « dimensionner le plafond `upto` selon `trustRobust` » reste une idée à tester (chantier 05 §4), et **aucune spec ne la soutient**.

### 3bis. `batch-settlement` (nouveau chez Monad)
[scheme_batch_settlement_evm.md](https://github.com/x402-foundation/x402/blob/main/specs/schemes/batch-settlement/scheme_batch_settlement_evm.md) (**DOC**) : canaux de paiement unidirectionnels. Le client fait un dépôt (via `receiveWithAuthorization` ou Permit2), puis signe hors chaîne des **bons cumulatifs** (*vouchers*), et le serveur les réclame par lots. `payerAuthorizer = address(0)` → bons vérifiés **en ERC-1271 contre le payeur**. C'est une option pour une démo « 1 000 micro-appels », mais la garde ANCRE ne jouerait alors qu'**au dépôt**, pas à chaque appel. Pas prioritaire.

### 6.2 Architecture (a) « un contrat refuse de payer » — la voie ERC-1271 (**DÉDUIT**, à prototyper)

Le payeur est un **compte-contrat** `TrustGatedPayer` qui détient les USDC et **n'a pas de clé privée**. Un opérateur (l'agent) signe pour lui, mais c'est le contrat qui décide. `isValidSignature(hash, blob)` :
1. décode `blob = abi.encode(to, value, validAfter, validBefore, nonce, agentId, opSig)` ;
2. **recalcule** le digest EIP-712 de `TransferWithAuthorization(from=this, to, …)` à partir du `DOMAIN_SEPARATOR` de l'USDC et exige `== hash`. Sans cette étape, le contrat signerait n'importe quoi, puisque `hash` seul ne révèle pas le destinataire ;
3. vérifie que `to` est bien le wallet de l'agent : `IdentityRegistry.getAgentWallet(agentId) == to` (ou l'owner ERC-721) ;
4. appelle `ANCRE.assess(agentId, setId)` et exige `status == OK` ;
5. vérifie `opSig` (ECDSA de l'opérateur autorisé sur `hash`) ;
6. renvoie `0x1626ba7e`, ou `0xffffffff` pour refuser (sans revert).

```solidity
// Esquisse, non compilée. setId engage θ, ρ, m, q, maxAge (D-décisions) ; aucun seuil en dur.
function isValidSignature(bytes32 hash, bytes calldata blob) external view returns (bytes4) {
    (address to, uint256 value, uint256 va, uint256 vb, bytes32 nonce, uint256 agentId, bytes memory opSig)
        = abi.decode(blob, (address, uint256, uint256, uint256, bytes32, uint256, bytes));
    bytes32 structHash = keccak256(abi.encode(TWA_TYPEHASH, address(this), to, value, va, vb, nonce));
    if (keccak256(abi.encodePacked("\x19\x01", USDC.DOMAIN_SEPARATOR(), structHash)) != hash) return 0xffffffff;
    if (IDENTITY.getAgentWallet(agentId) != to) return 0xffffffff;
    (uint8 status,) = ANCRE.assess(agentId, setId);           // doit être `view`
    if (status != STATUS_OK) return 0xffffffff;
    if (ECDSA.recover(hash, opSig) != operator) return 0xffffffff;
    return 0x1626ba7e;
}
```

Ce que cela apporte :
- **Le refus a lieu au moment du règlement, dans la tx du facilitator.** Un veto (slash) posé entre `/verify` et `/settle` fait échouer le règlement. C'est la scène du disjoncteur (D19) sans rien ajouter à x402.
- Compatible **sans aucune modification** du serveur, du facilitator ni du token.

Pièges à tester :
- **`isValidSignature` est `view`, et appelé en STATICCALL** par USDC et Permit2. `assess` doit donc être `view`, et **aucun event « refusé » ne peut être émis ici**. Pour l'écran (chantier 07), il faut soit un router non-view appelé avant, soit une reconstruction hors chaîne à partir de l'échec de `/verify`.
- **Gas** : `assess` coûte 77 à 190 k (`contracts/GAS.md`), plus ~6 k pour ecrecover, et c'est **le facilitator qui paie**, dans sa tx. Il faut vérifier que x402-rs estime ou fixe un gas limit suffisant (**NON TROUVÉ** dans le code lu). Sur Monad on paie la gas limit, et ce coût tombe sur le facilitator, pas sur nous.
- `validAfter/validBefore` restent en `block.timestamp` (imposé par l'USDC). Pour nos époques, nous gardons `block.number`.
- Côté client, le SDK TS signe avec un `signer` viem qui produit du 65 octets. Il faudra un **signer personnalisé** qui construit le `blob`. `x402Client.register(network, customScheme)` le permet.
- `payer` renvoyé par `/verify` et `/settle` = l'adresse du contrat. C'est cohérent pour un feedback ERC-8004 posté ensuite par ce même contrat (motif consommateur-ancre).

### 6.3 Pourquoi pas EIP-7702 (**DOC** + **DÉDUIT**)
- L'exemple officiel [clients/erc7702](https://github.com/x402-foundation/x402/blob/main/examples/typescript/clients/erc7702/index.ts) dit que le facilitator TS passe en ERC-1271 dès que l'adresse a du code, ce qui inclut une EOA déléguée par 7702.
- **Le facilitator Monad (Rust) fait autrement** : une signature de 65 octets qui retrouve `from` est traitée comme EOA et part vers `transferWithAuthorization(v,r,s)`, en ecrecover pur. Même avec un délégué 7702 gardé par ANCRE, **le propriétaire de la clé contourne la garde** en signant en brut.
- De plus, le délégué 7702 doit implémenter `isValidSignature`. Sinon, les facilitators « stricts » (TS) rejettent même les signatures légitimes.
- → 7702 convient à une garde **de confort** (l'agent n'a qu'une clé de session), pas à la preuve « le contrat refuse ».

### 6.4 ERC-7710 / MetaMask (lien avec le bounty D38)
- La spec `exact` décrit `assetTransferMethod: "erc7710"`, avec pour implémentation citée le **MetaMask Delegation Framework** ([gator.metamask.io](https://gator.metamask.io/)). Un *caveat enforcer* ANCRE (`beforeHook` qui appelle `assess` et revert) serait l'intégration la plus « native » pour le bounty *Best Agent Wallet Plugin*.
- **Mais le facilitator Monad ne l'annonce pas et x402-rs ne l'implémente pas** (**NON TROUVÉ**). Il faudrait héberger notre propre facilitator (TS `@x402/evm`) sur 10143. À instruire dans la recherche MetaMask.

### 6.5 Architecture (b) : gardes hors contrat (SDK)

**Côté client, avant signature** ([x402Client.ts](https://github.com/x402-foundation/x402/blob/main/typescript/packages/core/src/client/x402Client.ts), **DOC**) :
```ts
const client = new x402Client();
client.register("eip155:*", new ExactEvmScheme(account));
client.setSpendControls({ maxAmountPerPayment: "$1" });            // défaut "$1"
client.onBeforePaymentCreation(async ({ selectedRequirements }) => {
  const agentId = await resolveAgentId(selectedRequirements.payTo);   // wallet → agentId (8004)
  const [status, tag] = await publicClient.readContract({ address: ANCRE, abi, functionName: "assess", args: [agentId, SET_ID] });
  if (status !== STATUS_OK) return { abort: true, reason: `ANCRE ${status} (${tag})` };
});
// ou filtrage avant sélection : client.registerPolicy((v, reqs) => reqs.filter(isTrusted))
const fetchWithPayment = wrapFetchWithPayment(fetch, client);
```
C'est simple et gratuit (`eth_call`), mais c'est **l'agent** qui refuse, pas un contrat. C'est suffisant pour le plugin wallet et pour le mode dégradé.

**Côté serveur** : `x402ResourceServer.onBeforeVerify / onBeforeSettle` peuvent renvoyer `{abort:true, reason}`. Ils servent à filtrer **le payeur** : c'est ce que font #1395, #1484 et #2300. Ce n'est pas notre cas d'usage principal, mais ANCRE peut servir de « trust provider » pour ces crochets.

## 7. Extensions et propositions liées à l'identité, la réputation ou ERC-8004

### 7.1 Extensions présentes dans `specs/extensions/` (**DOC**, commit `02e80f3`)
`bazaar` (catalogue de découverte : `/discovery/resources`, `/discovery/search`), `builder-code` (attribution ERC-8021), `auth-hints`, `extension-offer-and-receipt`, `payment_identifier` (idempotence), `sign-in-with-x` (CAIP-122 ; SIWE avec EIP-1271 et 6492), `http-message-signatures`, et les deux de sponsoring de gas (`eip2612`, `erc20`).
→ **Aucune extension « reputation », « trust » ou « 8004 » n'a été fusionnée** (**NON TROUVÉ** dans les specs).

La plus proche est **`offer-and-receipt`** : le serveur signe en EIP-712 une offre et un **reçu** `{version, network, resourceUrl, payer, issuedAt, transaction?}`. Motivation citée : « verifiable proof of commercial interactions for reputation systems ». C'est une brique de **provenance** qui peut servir de preuve de paiement pour un avis 8004. Côté ANCRE, D3 s'applique : le paiement **n'entre pas** dans le poids.

Lecture :
- **#2641 est l'antériorité conceptuelle la plus proche** de « un contrat refuse de payer » : politique signée, preuve jointe au paiement, chemin `exact` inchangé. La différence avec ANCRE tient à trois points : la politique porte sur **la fiabilité du vendeur**, elle est **calculée et certifiée on-chain** (PPR relatif aux ancres choisies) au lieu d'un plafond et d'un marchand fixés à l'avance, et le **disjoncteur** coupe au bloc suivant. À citer honnêtement, au même titre que le PoC OpenRank (CLAUDE.md §6).
- Toutes les propositions « réputation » **produisent** des avis (#931, #1024, #2803) ou **filtrent le payeur** (#1395, #2300). Aucune ne lit une réputation **agrégée et résistante aux Sybil** avant de payer. C'est le créneau d'ANCRE, et ces fils sont les bons endroits pour la publication (chantier 06) en plus du #309 d'ethereum-magicians.
- Pour info, hors dépôt : **t402** propose un paquet Go `extensions/erc8004` ([pkg.go.dev](https://pkg.go.dev/github.com/t402-io/t402/sdks/go/extensions/erc8004)). Non lu en détail.

### 7.3 Comment un client x402 interrogerait ANCRE avant de payer (**DÉDUIT**)
1. Il reçoit le 402 et lit `accepts[i].payTo`.
2. Il résout `payTo` en `agentId` : par un index `agentWallet → agentId` (chantier 02, indexeur), par un champ d'extension déclaré par le serveur (par exemple `extensions["erc8004"].info.agentId`, **à proposer**, sans standard aujourd'hui), ou par `bazaar`.
3. Il fait un `eth_call` à `assess(agentId, setId)` : statut et tag déclencheur.
4. Il abandonne (`onBeforePaymentCreation` → `abort`) ou signe. En architecture (a), la même vérification est **rejouée on-chain** dans `isValidSignature` au moment du règlement.
Point à ne pas oublier : le serveur peut mentir sur `agentId`. Le contrat doit donc vérifier `getAgentWallet(agentId) == to` (étape 3 du §6.2).

## 8. Exemples minimaux pour la démo (**DOC**, [examples/typescript](https://github.com/x402-foundation/x402/tree/main/examples/typescript))

**Serveur Express, Monad testnet** (adapté de [servers/express](https://github.com/x402-foundation/x402/blob/main/examples/typescript/servers/express/index.ts) et de l'[exemple Monad](https://docs.monad.xyz/guides/x402)) :
```ts
import express from "express";
import { paymentMiddleware, x402ResourceServer } from "@x402/express";
import { ExactEvmScheme } from "@x402/evm/exact/server";
import { HTTPFacilitatorClient } from "@x402/core/server";

const NET = "eip155:10143", USDC_T = "0x534b2f3A21130d7a60830c2Df862319e593943A3";
const scheme = new ExactEvmScheme();
scheme.registerMoneyParser(async (amount, network) =>            // 10143 absent des assets par défaut
  network === NET ? { amount: Math.floor(amount * 1e6).toString(), asset: USDC_T, extra: { name: "USDC", version: "2" } } : null);

const app = express();
app.use(paymentMiddleware(
  { "GET /quote": { accepts: [{ scheme: "exact", price: "$0.001", network: NET, payTo: PROVIDER_WALLET }],
                    description: "Demo paid endpoint", mimeType: "application/json" } },
  new x402ResourceServer(new HTTPFacilitatorClient({ url: "https://x402-facilitator.molandak.org" }))
    .register(NET, scheme),
));
app.get("/quote", (_req, res) => res.json({ ok: true }));
app.listen(4021);
```
Il existe aussi une version Hono ([servers/hono](https://github.com/x402-foundation/x402/blob/main/examples/typescript/servers/hono/index.ts)), avec la même API (`@x402/hono` + `@hono/node-server`).

## 9. Pièges (récapitulatif)

1. **Dépôt** : lire `x402-foundation/x402`, pas `coinbase/x402` (figé le 2026-04-21).
2. **En-têtes** : v2 = `PAYMENT-SIGNATURE` et `PAYMENT-RESPONSE`. `X-PAYMENT` et `X-PAYMENT-RESPONSE` appartiennent à la v1. Le facilitator Rust gère aussi la v1 : bien vérifier `x402Version: 2`.
3. **USDC testnet ≠ mainnet** : `0x534b…43A3` contre `0x7547…b603`. Seul **143** figure dans `defaultAssets.ts` du SDK. Sur 10143, il faut un `registerMoneyParser` côté serveur et, côté client, `setSpendControls({allowedAssets…})` ou `false`, faute de quoi le plafond par défaut « $1 » ne reconnaît pas l'asset.
4. **Domaine EIP-712** : `name "USDC"`, `version "2"`. `eip712Domain()` revert, donc pas de découverte automatique.
5. **`upto`** : `@x402/evm ≥ 2.12.0`. `approve(Permit2)` est préalable (sinon **412**). `facilitatorAddress` est dans le témoin signé : **changer de facilitator invalide les signatures**. Le mode dégradé doit prévoir sa propre adresse.
6. **Erreurs du facilitator Monad** : une simulation qui échoue renvoie **HTTP 500 + `unexpected_error`** et un champ non standard `invalidReasonDetails`, pas un 402 typé. Ne pas se reposer sur `invalidReason` pour afficher la raison ANCRE.
7. **7702** : contournable (§6.3). **ERC-7710** : non supporté par le facilitator Monad (§6.4).
8. **ERC-1271 appelé en `view`** : `assess` doit être `view`, et aucun event n'est possible dans le chemin de refus.
9. **Temps** : `validAfter` strict (`now > validAfter`) et `validBefore` strict, en secondes. Le facilitator TS exige ≥ 6 s de marge. Avec 3 ou 4 blocs par seconde sur Monad, `maxTimeoutSeconds` à 60 suffit largement.
10. **Tiers** : le facilitator est un service Railway derrière Cloudflare, avec une seule EOA de règlement (`0x7f6a…`). Prévoir un mode dégradé : notre propre facilitator TS (`@x402/core` `x402Facilitator` + `@x402/evm`) sur 10143, ou un règlement direct.
11. **`batch-settlement`** vient d'apparaître chez Monad (absent le 23/09). Le catalogue de schémas bouge : **revérifier `/supported` le jour de la démo**.
