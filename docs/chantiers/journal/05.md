**Ce que je retiens**
1. **D39 est livré dans le contrat v1** : `isTrusted(agentId, setId)` applique toute la politique engagée dans le `setId` (θ, ρ, m, q, vetoMax, maxAge, eLowMax, mode strict). Le payeur **ne stocke aucun seuil** : sa politique se réduit à (`setId`, `maxPerPayment`). Les deux designs de la vague 2 (θ, ρ dans le payeur) sont périmés sur ce point.
2. `assess(…, true).trusted` et `isTrusted` donnent la même réponse (le second s'arrête avant la lecture du registre quand les bornes échouent). Le payeur appellera `isTrusted` dans `isValidSignature` (moins cher au refus) et `assess` dans `explain`/`decide` (pour le détail). Jamais le seul statut (AM-6.1).
3. `triggerTag` est un **hash** `keccak256(tag1)` (AM-04.2) : le plugin et l'écran doivent le résoudre via le schéma de tags, pas le décoder en texte.
4. Les deux designs divergent sur ce que signe l'opérateur : le digest USDC brut (payeur) ou une typed-data lisible `AncrePayment` dans le domaine du payeur (plugin). Je retiens **`AncrePayment`** (l'humain lit « payer #N » dans l'écran MFA, domaine cloisonné), raison ci-dessous à E1.
5. Le contournement réel est un `USDC.transfer` par une clé qui détient des USDC (AM-6.9) : le payeur doit être **le seul** détenteur, et sa sortie de fonds (`sweep`) ne doit aller qu'à une `treasury` immuable.
