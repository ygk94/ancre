**Ce que je retiens**
1. **D39 est livré dans le contrat v1** : `isTrusted(agentId, setId)` applique toute la politique engagée dans le `setId` (θ, ρ, m, q, vetoMax, maxAge, eLowMax, mode strict). Le payeur **ne stocke aucun seuil** : sa politique se réduit à (`setId`, `maxPerPayment`). Les deux designs de la vague 2 (θ, ρ dans le payeur) sont périmés sur ce point.
2. `assess(…, true).trusted` et `isTrusted` donnent la même réponse (le second s'arrête avant la lecture du registre quand les bornes échouent). Le payeur appellera `isTrusted` dans `isValidSignature` (moins cher au refus) et `assess` dans `explain`/`decide` (pour le détail). Jamais le seul statut (AM-6.1).
3. `triggerTag` est un **hash** `keccak256(tag1)` (AM-04.2) : le plugin et l'écran doivent le résoudre via le schéma de tags, pas le décoder en texte.
4. Les deux designs divergent sur ce que signe l'opérateur : le digest USDC brut (payeur) ou une typed-data lisible `AncrePayment` dans le domaine du payeur (plugin). Je retiens **`AncrePayment`** (l'humain lit « payer #N » dans l'écran MFA, domaine cloisonné), raison ci-dessous à E1.
5. Le contournement réel est un `USDC.transfer` par une clé qui détient des USDC (AM-6.9) : le payeur doit être **le seul** détenteur, et sa sortie de fonds (`sweep`) ne doit aller qu'à une `treasury` immuable.

## 2026-10-01 14:49 CEST — E1 : payeur ERC-1271 `TrustGatedPayer` — ✅

**Fait**
- `contracts/src/TrustGatedPayer.sol` (MIT, AM-6.6) : compte-contrat sans clé qui détient les USDC. `isValidSignature` (view, ne revert jamais) n'accepte que si : digest reconstruit = hash présenté (`from = this`) ; pas en pause ; montant ≤ `maxPerPayment` ; destinataire = `agentWallet(agentId)` ; `AncrePayment` signé par un opérateur ; **`isTrusted(agentId, setId)`** (D39, jamais le seul statut, AM-6.1).
- Trois sortes de blob, disposition fixe (`abi.encodePacked`, 246 / 266 / 98 octets, tous > 65 donc classés EIP-1271 par x402-rs) : 1 = EIP-3009 `exact`, 2 = Permit2 `upto` (via `x402UptoPermit2Proxy`), 3 = `cancelAuthorization`. Tout autre digest (permit EIP-2612, `PermitSingle`, `receiveWithAuthorization`…) est refusé.
- Lecture : `decide(agentId, to, value)` (garde douce du plugin, avant signature), `explain(hash, blob)` (raison + `Assessment` complet, pour l'écran), `reportRefusal(hash, blob)` (trace on-chain, sans permission, une fois par autorisation, seulement pour une autorisation authentique et encore réglable).
- Administration : owner (`setOperator` ≤ 4, `setPolicy(setId, maxPerPayment)`, `transferOwnership`, `approvePermit2`), pause (owner ; un opérateur peut seulement mettre en pause), `sweep` vers la `treasury` immuable uniquement (AM-6.9).
- Tests promus et réécrits : `test/TrustGatedPayer.t.sol` (45 unitaires, sur le vrai `AnchoredReputation` v1 + registres simulés + USDC simulé fidèle à FiatToken v2.2), `test/TrustGatedPayerFork.t.sol` (11 en fork, testnet **et** mainnet : vrais registres ERC-8004, vrai USDC, Permit2, proxy `upto`, `AnchoredReputation` v1 déployé dans le fork, ensemble **ouvert Registry-verified** k = 2, m = 2). Les 5 tests de la vague 2 sont couverts (dont 7702, AM-6.9).
- Scènes du brief, en fork : fournisseur fiable payé ; ferme (endossée par des Sybil) refusée ; inconnu (statut OK, trust 0) refusé ; veto d'une ancre → paiement suivant refusé au bloc suivant, sans recertification (D33) ; disjoncteur entre `/verify` et `/settle` ; `upto` payé puis refusé après veto.
- AM-INT.2 : chaque refus vérifie le message exact (`FiatTokenV2: invalid signature`, `EIP2612: invalid signature`, `InvalidContractSignature()` de Permit2) **et** l'absence de mouvement de fonds. Piège rencontré et corrigé : un `expectRevert` capte le premier appel externe suivant, y compris un `DOMAIN_SEPARATOR()` calculé dans les arguments.

**Décisions techniques**
1. Nom `TrustGatedPayer` (le `TrustGatedRouter` du brief dans sa version x402).
2. L'opérateur signe une typed-data **`AncrePayment`** dans le domaine du payeur (« ANCRE TrustGatedPayer », v1), pas le digest USDC brut : l'humain lit « to, value, agentId » dans l'écran MFA, et la signature ne vaut que pour ce payeur et cette chaîne.
3. Politique du payeur réduite à (`setId`, `maxPerPayment`) : θ, ρ, m, q, maxAge sont dans le `setId` (D39). `setPolicy` refuse un `setId` inconnu.
4. Blob à disposition fixe, lu sans `abi.decode` : `isValidSignature` ne revert jamais (fuzz : 2 × 256 cas).
5. Pas de repli `ownerOf` si `agentWallet = 0` : le wallet est effacé au transfert, et un agent transféré est `TRANSFERRED` de toute façon.
6. `isTrusted` dans `isValidSignature` (refus bon marché), `assess` dans `explain`/`decide` (détail), même verdict (test de parité sur 7 états).
7. Appels externes plafonnés à 120 k gas (comme `VIEW_CALL_GAS` d'ANCRE). Un plafond de 30 k sur `DOMAIN_SEPARATOR()` était **trop bas pour le vrai USDC froid sur Monad** (MESURÉ en fork : tout passait en DIGEST_MISMATCH via `eth_call`). Les bouchons ne l'avaient pas vu.

**Revues**

**Tests** : `forge test` (tout le dépôt, forks compris) : **147 verts** (91 existants + 45 + 11). Fork mainnet : 11 verts.

**Angles morts**
- **AM-05.1** : `agentWallet` n'est pas unique (178 wallets pour 1 773 agents, CLAUDE.md §3). Un serveur peut déclarer l'`agentId` d'un agent fiable qui partage son wallet : l'argent va bien à ce wallet, mais sur la réputation d'un autre agent. Limite de D20, documentée dans le contrat.
- **AM-05.2** : les bouchons sous-estiment les coûts froids de Monad (cf. décision 7) : toute garde doit être validée en fork.
- **AM-05.3** : un nœud sans ligne explicite est compté comme inconnu et gonfle `e` (0,444 au lieu de ~0 sur notre graphe de test) : le certificateur doit émettre des lignes vides pour les fournisseurs, sinon `distrustUp` fait échouer ρ. À vérifier côté solveur (chantier 04).
- **AM-05.4** : motif consommateur-ancre (D13) non implémenté : le payeur ne poste pas d'avis ERC-8004. Si on l'ajoute, **réservé à l'owner** : un opérateur compromis qui endosserait sa ferme deviendrait une ancre du payeur.
